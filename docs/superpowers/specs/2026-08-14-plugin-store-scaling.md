# 外掛商店的分類與規模化規劃

日期：2026-08-14
狀態：規劃，尚未實作

## 問題

現在 4 個外掛，單層清單就夠用。外掛長到十幾二十個時，「可安裝」那一區會變成一條
捲不完的清單，使用者找不到想要的東西。需要在它變成問題之前把分類的骨架想清楚，
但**不是現在就把 UI 做複雜**。

## 一、分類直接沿用 App 既有的五類

`src/lib/workspace.ts` 的 `PanelCategory` 已經定義好，而且使用者在「新增面板」
每天都在用：

| key | 標籤 | App 內建面板數 |
|---|---|---|
| `market` | 行情 | 13 |
| `trading` | 交易 | 5 |
| `derivatives` | 選擇權/衍生品 | 5 |
| `tools` | 工具 | 5 |
| `account` | 帳務分析 | 3 |

**不要為商店另創一套分類。** 外掛裝完就是變成面板，兩套分類法等於要使用者學兩次，
而且同一個東西在兩個地方叫不同名字。

首批四個外掛的歸類：

| 外掛 | 分類 |
|---|---|
| 證券對帳單 | `account` |
| 整戶與個股維持率 | `account` |
| 融資券到期明細 | `account` |
| 個股對應權證 | `derivatives` |

四個裡有三個是 `account`，這本身就是訊號：外掛補的正是 App 內建面板最少的那一類
（帳務分析只有 3 個內建面板），而 e-Leader 分析顯示帳務佔真實使用量 25.8%。

## 二、兩條正交的軸，不要混在一起

商店其實有兩種分法，現在的實作只用了第一種：

1. **狀態**：已安裝 / 可安裝 / 已停用 / 可更新
2. **類型**：上面那五類

狀態是「我跟這個外掛的關係」，類型是「這個外掛是什麼」。混在同一層會很亂
（例如把已安裝的對帳單放進「帳務分析」分類裡，使用者要找自己裝過的東西就得
先想它屬於哪類）。

**規則：狀態是外層，類型是內層。** 已安裝的永遠獨立在最上面，不被分類切散；
分類只用來切「可安裝」那一區。

## 三、依規模漸進，不要一次做滿

| 外掛數 | 商店長怎樣 | 何時做 |
|---|---|---|
| **1-10（現在）** | 現況：已安裝／可安裝兩區，單層清單 | 已完成 |
| **10-30** | 可安裝區加分類篩選列；已安裝維持單一清單 | 超過 10 個時 |
| **30+** | 加搜尋框；我的外掛與探索分成兩個 tab；加排序 | 超過 30 個時 |

門檻寫成常數（如 `CATEGORY_THRESHOLD = 10`），不要靠人工判斷什麼時候該改版。
外掛數一過門檻，那一列自己浮出來。

## 四、manifest 要加的欄位

```ts
// 沿用 workspace.ts 的 PanelCategory，不另立型別
category?: PanelCategory;
```

**設為 optional**：舊 manifest 沒有它仍然有效，UI 端缺值歸到 `tools`（工具是
天然的收容所）。`parseManifest` 驗證值必須是五個合法 key 之一，未知值拒絕
（比照 permissions 的處理）。

**分類掛在外掛層，不是面板層。** 一個外掛可以提供多個面板（`activate` 回傳
`panels` 陣列），那些面板各自的分類由 `PluginPanelDef` 決定、給 panel-library 用；
商店只需要一個「這個外掛主要是做什麼的」的標籤。

## 五、規模化時會踩到但現在還沒感覺的三件事

### 1. 批次更新

4 個外掛各按一次更新已經很煩，30 個不可能。可更新數 >= 3 時在「已安裝」區塊
標題右側出現「全部更新」。

實作上要注意：更新是逐一走 `updatePlugin`，其中任何一個失敗不能中斷其他的
（比照 `initPlugins` 的逐外掛隔離），失敗的留在原地並顯示原因。

### 2. 來源信任標示

開放第三方上架之後，「官方發佈」與「某人寫的」必須一眼可辨。現在只有
side-load 有琥珀副徽章，因為目前所有 catalog 內的外掛都是官方的。

建議 manifest 加 `publisher?: string`，商店顯示發佈者，官方的加一個已驗證標記。
這件事與權限揭露是同一個目的的兩面：權限講「它能碰什麼」，發佈者講「誰讓它碰」。

### 3. 分類本身會不夠用

五類是為 App 內建面板設計的。外掛生態長出來之後可能出現不屬於任何一類的東西
（例如「AI 助理擴充」「資料匯出工具」）。屆時要嘛擴充 `PanelCategory`（會動到
upstream 檔案，增加 fork 衝突面），要嘛在商店端另建一層映射。

**現在不要為此設計。** 等真的出現第六類需求再處理，那時才知道它該叫什麼。

## 六、不做（YAGNI）

- **精選／推薦區**：要有排序依據（下載數、評分）才有意義，那是後端服務的規模，
  現在 store.json 是一個靜態檔
- **評分與評論**：同上，需要後端
- **分類的巢狀階層**：五類配三十個外掛，一層就夠
- **外掛截圖／預覽圖**：CSP 擋外部圖片，要做得內嵌進 bundle，成本高於價值；
  現在的圖示＋描述已經夠辨識
